PH-001

QueryParamDict.to_text leaves ';' unquoted in values, but parse_qsl splits pairs on ';'

wrong result medium confidence 0.72 failed 3/3

boltons.urlutils.QueryParamDict.to_text · boltons/urlutils.py

Input
QueryParamDict([('a', 'b;c')]).to_text(full_quote=True)
Expected
';' within a value is percent-encoded (%3B), so parsing the output returns [('a', 'b;c')]
Actual
Output is 'a=b;c', which from_text parses as [('a', 'b'), ('c', None)]
Property
from_text(to_text(d)) gives back the same items as d, for any string keys/values and either full_quote setting
Repro test 
from boltons.urlutils import QueryParamDict


def test_repro_semicolon():
    d = QueryParamDict([('a', 'b;c')])
    text = d.to_text(full_quote=True)
    assert QueryParamDict.from_text(text).items(multi=True) == [('a', 'b;c')], text

AssertionError: a=b;c

Why this is a bug

to_text docs: full_quote=True percent-quotes special characters (fully-quoted URLs are 'necessary for sending over the network'). _QUERY_SAFE keeps sub-delims such as ';' unquoted, while parse_qsl in the same module splits on both '&' and ';', so the two halves of the module disagree and data is corrupted.

Independent review: _QUERY_SAFE removes only '&', '=' and '+' from the safe set, so ';' is written raw. The module's own parse_qsl splits on both '&' and ';', so QueryParamDict.from_text(to_text(d)) turns ('a','b;c') into ('a','b'),('c',None). This silently corrupts data, and the loss happens even with full_quote=True, which is meant for sending over the network. Nothing in the tests relies on ';' staying unquoted in query values. Quoting ';' in query parts (or dropping the ';' split in parse_qsl, as CPython did) is a small change a maintainer would likely accept.

Hypothesis shrank it to: Failing test case: test_qp_roundtrip_blank( pairs=[( '0', # or any other generated value ';', )], )

Why this is a bug

Stats has a `default` for empty data and get_quantile/describe handle empty data; get_histogram_counts explicitly handles empty data by returning [(0.0, 0)] (_get_bin_bounds returns [0.0]), but format_histogram_counts divides by the max count, which is 0.

Independent review: Stats supports empty data, and get_histogram_counts deliberately returns [(0.0, 0)] for it (_get_bin_bounds returns [0.0]). format_histogram_counts then computes `float(bar_cols) / count_max` with count_max == 0 and crashes. Nothing documents or tests this as an intended error, and the guard is trivial (for example, treating a zero count_max as 1), so a maintainer would likely accept the fix. The impact is a narrow edge case, hence low severity.

PH-004

relative_time() drops requested decimal digits because it formats with :g (6 significant digits)

wrong result low confidence 0.60 failed 3/3

boltons.timeutils.relative_time · boltons/timeutils.py

Input
d=datetime(2000,1,1), other=d+timedelta(seconds=1, microseconds=123456), ndigits=6
Expected
'1.123456 seconds ago'
Actual
'1.12346 seconds ago'
Property
the number printed by relative_time equals the value returned by decimal_relative_time rounded to ndigits
Repro test 
from datetime import datetime, timedelta
from boltons.timeutils import relative_time


def test_repro_relative_time_ndigits():
    d = datetime(2000, 1, 1)
    other = d + timedelta(seconds=1, microseconds=123456)
    assert relative_time(d, other, ndigits=6) == '1.123456 seconds ago'

AssertionError: assert '1.12346 seconds ago' == '1.123456 seconds ago'

Why this is a bug

Docstring: ndigits is 'The number of decimal digits to round to'. decimal_relative_time returns 1.123456, but relative_time formats with f'{abs(drt):g}', which keeps only 6 significant digits, so the requested precision is silently lost.

Independent review: The docstring says ndigits is the number of decimal digits to round to, and decimal_relative_time rounds correctly to 1.123456. relative_time then formats with f'{abs(drt):g}', which keeps only 6 significant digits, so the printed value is 1.12346. The same happens whenever the integer part plus ndigits exceeds 6 digits, for example 12.123456 with ndigits=6 prints 12.1235. The :g format is there to drop trailing zeros ('0 seconds ago'), and a fix could keep that. The impact is narrow, since ndigits above 5 is rare, and no existing test covers it.

Hypothesis shrank it to: Failing test case: test_relative_time_ndigits( d=datetime.datetime(2000, 1, 1, 0, 0), # or any other generated value secs=1, nd=6, )
