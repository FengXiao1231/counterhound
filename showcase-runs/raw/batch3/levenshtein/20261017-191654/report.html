Why this is a bug

Docstring: 'If maxCost is non-zero, the calculation stops as soon as the distance is determined to be greater than maxCost. Therefore, any return value higher than maxCost is a lower bound for the actual distance.' Implied: a value <= maxCost is exact. Similarity/Match docs: scores lower than MinScore are returned as 0; here a 0.25 score is reported as 0.75.

Independent review: The input is valid (non-negative costs, maxCost=2). By my hand calculation the true distance for "aaa"→"bbbab" with ins=1, sub=2, del=2 is 6: two substitutions, one match and two insertions. The docs promise that only values above maxCost may be lower bounds, so a value ≤ maxCost should be exact. package levenshtein

import "testing"

func TestReproPrefixAfterScale(t *testing.T) {
	p := NewParams().BonusScale(0.25).BonusPrefix(10)
	s := Match("aaaaaaaaaaaaaaaaaaab", "aaaaaaaaaaaaaaaaaaac", p)
	if s > 1 {
		t.Fatalf("Match = %v, want <= 1", s)
	}
}

AssertionError: Match = 1.0750000000000002, want <= 1

No fix: not attempted: --budget was used up

Why this is a bug

Doc: 'To guarantee that the similarity score remains in the interval 0..1, this scaling factor is not allowed to exceed 1 / BonusPrefix.' The clamp is only applied inside BonusScale, so a later BonusPrefix(v) (which does not re-clamp) breaks the invariant; Similarity range 0..1 is promised for Match.

Independent review: The BonusScale doc says the scale is "not allowed to exceed 1 / BonusPrefix" so that the score stays within 0..1. The clamp runs only inside BonusScale (params.go:136), and BonusPrefix (params.go:118) sets the value without re-checking. So `BonusScale(0.25).BonusPrefix(10)` gives prefix*scale = 2.5. Match then computes sim + pl*scale*(1-sim) = 0.95 + 10*0.25*0.05 = 1.075, which is real arithmetic and not a float artefact. The same state can also make the `1 - bonusPrefix*bonusScale` divisor in the minScore pre-computation (levenshtein.go:268) zero or negative. A maintainer would likely fix this by re-clamping in BonusPrefix or clamping at use time in Match.

func TestReproZeroCostNaN(t *testing.T) {
	p := NewParams().InsCost(0)
	for _, v := range []float64{Similarity("", "a", p), Match("", "a", p)} {
		if math.IsNaN(v) || v < 0 || v > 1 {

		}
	}
}

Why this is a bug

Docs: 'The score is in the range of 0..1'; costs 'must be zero or positive' so 0 is explicitly allowed; the code comment shows the author intends to avoid divByZero issues but only guards the both-empty case.

Independent review: InsCost(0) is documented as valid ("must be zero or positive"), and Match is documented to return a score in 0..1. For ("", "a") with InsCost(0), l1=0 and l2=1, so maxDist = 0*delCost + 1*0 = 0 and dist = 0. Line 276 then computes 1 - 0/0, which is NaN. The only guard is the both-empty shortcut at line 230, and its comment says it exists to avoid divide-by-zero. The same case can arise with other zero-cost configurations. A maintainer would likely accept a small fix that returns 1, or a defined value, when maxDist == 0.
