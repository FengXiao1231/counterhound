PH-001

removeOne() with a negative index corrupts the queue because the branch choice uses the un-normalised index

wrong result medium confidence 0.93 failed 3/3

Denque.prototype.removeOne · index.js

Input
new Denque([1,2]).removeOne(-1)
Expected
returns 2 and the queue becomes [1]
Actual
returns 2 but the queue becomes [undefined, 1]-like corrupted state (the front slot is cleared and head advanced instead of removing the last item)
Property
removeOne(i) behaves like Array.prototype.splice(i,1) on the equivalent array, including negative indices, leaving the remaining items intact
Repro test 
import test from 'node:test';
import assert from 'node:assert/strict';
import Denque from '../../../../../index.js';

test('repro_removeone_negative', () => {
  const d = new Denque([1, 2]);
  assert.equal(d.removeOne(-1), 2);
  assert.deepEqual(d.toArray(), [1]);
});

AssertionError: Expected values to be strictly deep-equal:

Why this is a bug

removeOne explicitly accepts negative indices (range check i < -size, then i += size), and peekAt documents negative indices as counting from the end. The shifting branch is chosen with the un-normalised `index` (index < size/2), so a negative index always takes the front branch with a zero-iteration loop.

Independent review: removeOne explicitly accepts negative indices (`i < -size` is rejected, otherwise `i += size`), but the branch test `index < size / 2` and the loop counters still use the original `index`. With index -1, the front branch is taken with a zero-iteration loop. It then clears the slot of the last element and advances `_head`, so the queue ends up as [undefined] instead of [1]. The fix is to use the normalised `i` for the branch test and loop counts, which a maintainer would accept.

PH-002

remove() with a negative index and count > 1 corrupts the queue

wrong result medium confidence 0.90 failed 3/3

Denque.prototype.remove · index.js

new Denque([1,2,3,4]).remove(-3, 2)
Expected
returns [2,3] and the queue becomes [1,4]
Actual

Repro test 
import test from 'node:test';
import assert from 'node:assert/strict';
import Denque from '../../../../../index.js';

test('repro_remove_negative', () => {
  const d = new Denque([1, 2, 3, 4]);
  assert.deepEqual(d.remove(-3, 2), [2, 3]);
  assert.deepEqual(d.toArray(), [1, 4]);
});

AssertionError: Expected values to be strictly deep-equal:

Why this is a bug

remove() accepts negative indices (i < -size check, i += size) but the later branches use the raw `index` (index + count === size, index === 0, index < 0) instead of the normalised i.

Independent review: remove() explicitly accepts negative indices (`i < -size` check, then `i += size`). After that, the multi-item branches still test and use the raw `index` (`index + count === size`, `index === 0`, `this._head + index + count`, `index < 0`) instead of the normalised `i`. For `remove(-3, 2)` on [1,2,3,4], none of the fast paths match and the middle-removal branch uses a negative `index`. That leaves `undefined` holes and wrong contents, as the repro shows. The `count === 1` path uses the normalised `i` and works, and positive indices are unaffected, so this is an incomplete normalisation that a maintainer would fix.
