PH-001

stringify() sorts the caller's filter array in place when a sort option is supplied

wrong result low confidence 0.75 failed 3/3

stringify (lib/stringify.js module.exports) · lib/stringify.js

Input
stringify({i:1,a:2}, {filter:['i','a'], sort:(a,b)=>a.localeCompare(b)})
Expected
Output 'a=2&i=1' and the caller's filter array remains ['i','a']
Actual
Output is sorted, but filter is mutated to ['a','i'] (objKeys = filter; objKeys.sort(...))
Property
stringify does not mutate its input options (the filter array) when sort is supplied
Repro test 
import test from 'node:test';
import assert from 'node:assert/strict';
import stringify from '../../../../../lib/stringify.js';

test('repro_filter_mutation', () => {
  const filter = ['i', 'a'];
  const out = stringify({ i: 1, a: 2 }, { filter, sort: (a, b) => a.localeCompare(b) });
  assert.equal(out, 'a=2&i=1');
  assert.deepEqual(filter, ['i', 'a']);
});

AssertionError: Expected values to be strictly deep-equal:

Why this is a bug

Top-level code does `objKeys = filter; ... objKeys.sort(options.sort)`, sorting the user's array. Inner recursion sorts a fresh Object.keys copy, so only the filter path leaks the mutation; a serializer is expected not to modify its options, and reusing one filter array across calls is the documented usage.

Independent review: In lib/stringify.js, module.exports sets `objKeys = filter` (the caller's array) and then calls `objKeys.sort(options.sort)`. This reorders the array the caller passed in. The recursive path avoids this because it sorts a fresh `Object.keys` copy. The README documents `filter` as a reusable list of keys and never says it may be reordered, and a serializer silently mutating its options is a surprising side effect. The repro is correct and fails consistently, and the fix is trivial: use `filter.slice()` or copy before sorting. A maintainer would likely accept it, but it is a minor edge case with no documented guarantee, which is why the severity is low.

Repro test 
import test from 'node:test';
import assert from 'node:assert/strict';

test('repro_comma_numeric_entities', () => {
  assert.deepEqual(

    { a: ['b', 'c'] }
  );
});

AssertionError: Expected values to be strictly deep-equal:

Why this is a bug

parseValues splits the value into an array via parseArrayValue (comma:true), then `val = interpretNumericEntities(String(val))` at lib/parse.js:191 stringifies the array with Array#toString, rejoining it with ',' and returning a string. The README documents comma:true as parsing comma-separated values into arrays; without interpretNumericEntities the same input yields ['b','c'].

Independent review: In lib/parse.js, `interpretNumericEntities(String(val))` runs on the array that `parseArrayValue` returns for comma:true. `String()` joins it with ',' and the result is a string, so `a=b,c` gives 'b,c' instead of ['b','c']. This is the only comma:true case where an option that should only rewrite values changes the result's shape, and the README promises arrays. One weakness: the existing test at test/parse.js:1292 asserts the joined output (`a[]=1,☺` gives `['1,☺']`). That test is titled 'does not crash', so it looks like it locked in the accident, but a fix would have to update it.
