PH-001

A lone single-quote value is parsed as an empty string (stringify/parse round-trip fails)

wrong result low confidence 0.85 failed 3/3

ini.parse (unsafe/isQuoted) · lib/ini.js

Input
{a: "'"}
Expected
{a: "'"}
Actual
{a: ''}
Property
unsafe(safe(s)) === s / parse(stringify(obj)) deep-equals obj
Repro test 
import test from 'node:test';
import assert from 'node:assert/strict';
import mod from '../../../../../lib/ini.js';

test('repro_single_quote_char', () => {
  assert.deepEqual({ ...mod.parse(mod.stringify({ a: "'" })) }, { a: "'" });
});

AssertionError: Expected values to be strictly deep-equal:

Why this is a bug

safe() guards its quote check with val.length > 1, so a lone "'" is emitted unquoted, but unsafe()'s isQuoted has no length check: a single quote both starts and ends with "'", so slice(1,-1) yields ''. The two halves are inconsistent.

Independent review: In lib/ini.js, safe() deliberately skips quoting when val.length > 1 is false, so "'" is written unquoted as `a='`. unsafe() then calls isQuoted("'"), which is true because the string both starts and ends with "'". The single-quote branch slices it to '', and JSON.parse('') throws and is ignored, so the value becomes ''. A lone `"` survives because JSON.parse fails and leaves it unchanged, so the single-quote path is the only broken one. The repro uses the API correctly and a one-character value is a valid string, so a length check in unsafe's quote handling would be an easy fix a maintainer would likely accept. The impact is narrow.

PH-002

stringify/parse does not round-trip string values with a backslash before ';' or '#'

wrong result low confidence 0.80 failed 3/3

ini.stringify / ini.parse · lib/ini.js

Input
{a: '\\;'} (a backslash followed by a semicolon)
Expected
parse(stringify({a:'\\;'})) -> {a:'\\;'}
Actual
{a:'\\'} (the ';' is treated as a comment start)
Property
parse(stringify(obj)) deep-equals obj for string values
Repro test 
import test from 'node:test';
import assert from 'node:assert/strict';
import mod from '../../../../../lib/ini.js';

test('repro_backslash_semicolon', () => {
  assert.deepEqual({ ...mod.parse(mod.stringify({ a: '\\;' })) }, { a: '\\;' });
});

AssertionError: Expected values to be strictly deep-equal:

Why this is a bug

stringify escapes ';' and '#' with a backslash but does not escape a preceding backslash, so the output 'a=\\;' is read by parse as an escaped backslash followed by an unescaped comment marker. encode/decode are a documented inverse pair, and safe() exists to make values round-trippable.

Independent review: `unsafe()` treats `\\` as an escaped backslash, and `\;` or `\#` as an escaped comment character. `safe()` escapes only `;` and `#`, and never escapes the backslash. So the value `\;` is written as `\;`, which `unsafe()` reads as a backslash followed by an unescaped `;`. The rest of the value is dropped as a comment, so data is silently lost. The same asymmetry loses data for any value with consecutive backslashes (`\\` comes back as `\`). `safe()` and `unsafe()` are exported as a pair, and `safe()` already falls back to `JSON.stringify` for other values that would not survive, so a small fix is plausible, such as quoting values that contain a backslash next to a backslash, `;` or `#`. The input is a valid string and nothing in the code or tests excludes it. The only doubt is that the corner case is narrow and the README makes no explicit round-trip promise.
